# Plan de implementación — Panel de BI de ventas

- **Fecha:** 2026-09-04
- **Spec asociado:** `docs/superpowers/specs/2026-09-04-bi-ventas-design.md`
- **Estado:** Reconstruido a partir de la transcripción de la sesión original (mismo stack y
  mismas 8 tareas acordadas; el documento fuente no se conservó).

## Stack tecnológico

| Capa | Elección |
|---|---|
| Framework web | Next.js 14 (App Router, TypeScript) |
| Base de datos | Postgres (Neon, serverless) |
| ORM | Prisma |
| Autenticación | NextAuth.js, Credentials Provider (usuario/clave propios) |
| Lectura de Excel | `exceljs` |
| Origen del Excel | Microsoft Graph API (permisos de aplicación) |
| Gráficos | Recharts |
| Estilos | Tailwind CSS |
| Hosting | Vercel |
| Sincronización diaria | Vercel Cron → API route protegida |

Justificación breve: es el stack que minimiza mantenimiento para un no-programador (Vercel +
Neon son "serverless", sin servidores que administrar; NextAuth evita construir auth a mano;
Prisma da migraciones versionadas y tipadas).

## Principio de ejecución: TDD real en cada tarea

Cada tarea se ejecuta como: **test que falla → implementación mínima → test que pasa → commit**.
Los tests se corren de verdad (`npm test` / `npx vitest run` / `npx playwright test` según
corresponda) antes de dar una tarea por cerrada — no se documentan como si hubiesen pasado sin
ejecutarlos.

## Tarea 1 — Modelo de datos

**Objetivo:** esquema Prisma que soporte hechos de venta a nivel de línea, con las dimensiones de
filtrado del spec (producto, marca, categoría, vendedor, zona) y lo necesario para calcular
margen, YoY y WoW.

Entidades: `Product` (con `brand`, `category`), `Salesperson`, `Zone`, `SaleLine` (fecha, producto,
vendedor, zona, cantidad, precio unitario, costo unitario), `SyncRun` (auditoría de cada corrida
del job diario: fecha, filas procesadas, estado, error).

TDD:
1. Test de integración que inserta un `SaleLine` con sus relaciones y verifica que se puede leer
   de vuelta con los campos calculados disponibles (falla: no existe el schema).
2. `npx prisma init`, definir `schema.prisma`, `npx prisma migrate dev`.
3. Test pasa contra una base Postgres de prueba.
4. Commit.

## Tarea 2 — Cálculo de métricas (margen, YoY, WoW)

**Objetivo:** módulo puro (sin I/O) que recibe líneas de venta y devuelve métricas agregadas.

- Margen $ = Σ(precio_unitario − costo_unitario) × cantidad
- Margen % = Margen $ / Ventas $
- YoY = (período_actual − mismo_período_año_anterior) / mismo_período_año_anterior
- WoW = (semana_actual − semana_anterior) / semana_anterior
- Manejo explícito de división por cero (período base en 0 → crecimiento indefinido, no error).

TDD: casos unitarios por métrica, incluyendo bordes (sin datos históricos, denominador 0,
desglose por cada dimensión) antes de escribir la función.

## Tarea 3 — Descarga y parseo del Excel desde OneDrive

**Objetivo:** cliente de Microsoft Graph API (client credentials flow, permisos de aplicación)
que descarga el archivo por su path/driveId y un parser con `exceljs` que lo transforma en filas
tipadas, validando columnas esperadas.

TDD: parser probado primero contra un `.xlsx` de fixture (sin red); el cliente de Graph probado
con la llamada HTTP mockeada (sin depender de credenciales reales en tests). Las credenciales
reales de OneDrive del usuario se configuran recién en la Tarea 8, cuando haya conectividad y
Azure AD esté registrado.

## Tarea 4 — Job diario de sincronización

**Objetivo:** API route (`/api/sync`) protegida por secreto, invocada por Vercel Cron, que
encadena: descargar Excel → parsear → recalcular métricas → persistir → registrar `SyncRun`.
Idempotente (una corrida del mismo día no duplica datos).

TDD: test de integración que simula dos corridas seguidas sobre el mismo dataset y verifica que
no hay duplicados; test de que una corrida fallida (Excel corrupto, Graph caído) queda registrada
como error sin tumbar datos previos.

## Tarea 5 — Login propio

**Objetivo:** NextAuth con Credentials Provider, usuarios almacenados en Postgres (password
hasheado con bcrypt), páginas protegidas por sesión.

TDD: test de que un login con credenciales inválidas es rechazado; test de que rutas del
dashboard sin sesión redirigen a login; test de que credenciales válidas crean sesión.

## Tarea 6 — Endpoint del dashboard con filtros

**Objetivo:** API interna que recibe filtros (producto, marca, categoría, vendedor, zona, rango
de fechas) y devuelve las métricas agregadas ya calculadas (lee de Postgres, nunca del Excel).

TDD: tests de la capa de query con distintas combinaciones de filtros, incluyendo "sin filtros"
(agregado total) y combinaciones múltiples.

## Tarea 7 — Panel visual (frontend)

**Objetivo:** dashboard en Next.js con tarjetas de métricas (ventas $/cantidad, margen $/%, YoY,
WoW) y gráficos (Recharts) desglosables por las 5 dimensiones, con la paleta de marca.

- Paleta: naranjo de marca (hex a extraer inspeccionando visualmente allnutrition.cl — ver nota
  en el spec) sobre base blanco/negro. Placeholder mientras tanto: `#F5821F`.

TDD: tests de componente (render con datos de fixture, verificar que los filtros disparan
refetch, verificar accesibilidad básica de las tarjetas).

## Tarea 8 — Despliegue en Vercel + registro de la app en Azure AD

**Objetivo:** proyecto desplegado en Vercel, con Postgres (Neon) conectado, variables de entorno
configuradas, Vercel Cron activo para la Tarea 4, y una app registrada en Azure AD con permisos
de aplicación de Microsoft Graph (`Files.Read.All` o el permiso mínimo necesario sobre el drive
específico) con consentimiento de administrador otorgado.

Este paso requiere interacción directa con el usuario (no se puede automatizar completo): crear
la app en el portal de Azure, generar el client secret, identificar el `driveId`/`itemId` del
Excel, y cargar esos valores como variables de entorno en Vercel.
